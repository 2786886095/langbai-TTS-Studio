# 1.3.0 长文工作台与 Breeze 接入

本文描述 v1.3.0 的 P0 长文核心与 P1 工作台。各项验收范围和限制单独列出，不代表全部真实引擎和打包场景均已验收。[GitHub Release](https://github.com/2786886095/langbai-TTS-Studio/releases/tag/v1.3.0)

## 两个入口，共用任务

- 桌面：双击仓库根目录的 `Start-Langbai-TTS-Studio.cmd`。它使用本地 Electron 和已构建前端，不启动 Vite；若没有 `frontend/dist/index.html`，先用已有前端依赖构建。
- 网页：双击 `Start-Longform-Web.cmd`。只运行任务服务并打开 `http://127.0.0.1:18765/longform`，不要求桌面窗口保持打开。

这两个源码入口要求已经准备 `node_modules`、前端依赖及 `backend/.venv`。入口不会创建新的依赖安装、权重下载任务或复制参考音频，Breeze 不提供自动下载器；旧安装器中已有用户确认的未完成任务仍按原恢复机制处理。推理模型在用户发起生成或明确启动引擎时加载，单纯打开界面不会新加载模型。准备依赖仍使用 README 的开发步骤。

默认数据目录为当前用户的 Windows“文档”目录下 `langbai-TTS-Studio/data`。例如本次开发机器的实际目录是 `D:\Documents\langbai-TTS-Studio\data`；其他机器不应硬编码为 D 盘。

需要明确使用其他本机目录或端口时：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-LocalStudio.ps1 -Mode Desktop -DataRoot "D:\Documents\langbai-TTS-Studio\data" -Port 18765
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-LocalStudio.ps1 -Mode Web -NoBrowser
```

启动器仅复用 `/health` 同时满足以下条件的服务：`service=langbai-TTS-Studio-v2`、`protocolVersion=2`、`schemaVersion=2`、数据目录一致。不兼容的端口占用会拒绝启动，不会结束已有进程。后台服务的启动输出记录在数据目录的 `logs/`；Electron 既有桌面日志也可从诊断入口查看。

首次运行可能先做逐文件备份。启动器等待超时不会杀掉正在备份的服务，请先检查日志，避免重复启动。

## 长文生成

1. 粘贴或导入正文。编辑草稿自动保存在当前浏览器配置中；提交后，原文另存为不可变 UTF-8 文档。
2. 选择引擎和对应声音资料。每个引擎的声音资料相互独立；GPT-SoVITS 仍使用成对 GPT/SoVITS 权重及准确参考文字。
3. 预览分段，检查环境和参考声音。可以先用短段试听。
4. 点击生成。任务经过准备与校验、等待显卡、加载、预热、正文生成、合并、导出和成品校验。
5. 成品发布后下载或试听完整音频，也可以逐段试听。

中文首版预算为最多 10 万汉字、50 万总字符。Breeze 默认策略沿用已验证的中文算法：目标约 110 汉字、上限 120 汉字，同时增加单请求 300 总字符硬上限。中英混排、纯英文、长数字和无标点文本有有界切分或明确拒绝规则；非中文长文的生成质量尚未验收。

分段保存原文 `[start,end)` 位置、实际发送文字及规范化规则。所有来源区间拼接必须与保存的原文逐码点一致；参考文字与发音是否准确仍需听音确认，文件校验不能替代逐字核听。

## 暂停、恢复与局部重做

- **段后暂停**：完成并验收当前段后暂停。模型可以短时保持热状态，空闲超时后卸载；继续时以实际 worker 状态决定是否重新加载、预热。
- **立即停止**：请求终止当前尝试，该段不计为完成，下次重新生成。不能确认 Linux worker 已退出时显示“停止尚未确认”，不会伪报成功。
- **中断恢复**：服务或 worker 意外退出后，重新打开任务并点继续。已有片段逐一校验 hash，只生成缺失、损坏或配置失效的片段。
- **局部重做**：可对指定分段显式换种子；旧片段和请求身份用于追溯。编辑文字后创建新任务，满足复用条件的片段可以沿用。
- **重新导出**：只改输出格式、采样率或段间停顿时，复用已验收的音频，不重新调用模型。

当前重新导出仍会核对原引擎安装、参考文件和指纹；移动或删除原安装后，仅凭片段进行独立离线导出尚未开放。

默认保留分段。关闭“保留分段”会放弃后续续跑、单段重做和重新导出；其他任务仍在引用的共享音频不会被删除。清理在完整成品和完成状态持久化后进行，事务失败时保留片段与“清理待处理”状态；清理警告不会把已经保存的成品撤回为失败。取消任务后按“复制为新任务”继续，不把已取消状态静默改回运行。

存储冲突使用有界重试；用尽后进入“存储受阻”，排除占用后可继续。I/O 恢复与模型重试分开记录。截断或验收失败只有有限次重试和自动拆分，仍失败时停在待处理状态。

## 进度与计时

正文进度按“已验收段 / 总段数”计算。正文达到 100% 后仍可能处于合并、导出或校验阶段；只有成品校验、原子发布后才显示完成。

界面分别显示总等待、有效处理、模型生成、暂停和未知中断间隔。宿主机在每个会话内使用单调时钟，持久化 UTC 锚点；跨进程无法还原的时间不会用 0 或估算值冒充。worker 自报的计时保存在元数据中，不和宿主计时混加。剩余时间需积累同一个热 worker 的样本后才给出估算区间。

P1 使用 SSE 发送变化的任务摘要，断线时保留轮询回退；不会持续向前端重传整篇文稿和全部分段。分段与事件日志按页读取。

## 格式与采样率

以下为默认 v2 长文工作台的输出契约；保留的旧原生/多人创作入口仍使用旧任务 API，不能把 v2 的恢复和输出能力推定到旧清单上。

- WAV、FLAC 可用；检测到已安装并校验的受管理 FFmpeg 后才显示 MP3。
- “引擎原生”从实际音频读取采样率，不回落为 44100 Hz。Breeze 为 24000 Hz 单声道。
- 指定其他采样率时在导出阶段统一转换。完整音频按片段流式合并，不把全书 PCM 同时装入内存。
- 合并和编码先写临时文件，校验后再发布成品。中途失败时保留可恢复的任务和片段。

## Breeze：默认 accelerated

首版只读绑定已经安装的 WSL 运行环境，不提供 Breeze 自动安装或权重下载。绑定字段包括 Windows 源码与模型目录、WSL 发行版、Linux Python 绝对路径。

本次已验证环境为 `F:\AI\Breeze-TTS-2`、Ubuntu、Linux Python `/home/langbai666/.venvs/breeze-tts-2/bin/python`。这些只是本机配置示例；其他机器需要填写自己的路径。

默认性能配置固定为 **accelerated、CFG=1 参考声音克隆**：主干解码 CUDA Graph、深度解码器编译，准确参考文字必填，声音描述留空。worker 校验固定源码、权重与 KV 修复指纹，不会替用户修改现有安装。

桌面与网页的长文任务只使用任务服务启动的一个 Breeze worker。独立 Gradio 短句页面可能另持一份模型，12 GB 显卡不适合同时加载两份；软件显示外部占用并等待用户处理，不会自动杀掉外部服务。现有 Gradio 的“长文本”入口只是共享网页的入口，不另建长文队列。

原生 Windows 推理、其他 CFG、声音设计、情绪指令、Breeze 训练和 Breeze 多人配音都未作为已支持能力开放。GPT-SoVITS 已有多人模式继续保留。

## 数据、备份和回滚

v2 数据放在独立 `data/v2/`：原文 `documents/`、临时产物 `staging/`、验收片段 `renders/`、完整成品 `outputs/`、数据库 `studio.db`。不会往旧版项目或声音扫描目录添加不兼容的附加 JSON。

首次运行对旧 `jobs/`、`projects/`、`voice-profiles/` 做副本和逐文件 hash 校验，备份位置及台账写入 `v2/migration.json`。备份空间不足或源文件在复制中变化会停止迁移；启动锁在任何恢复写入前取得。

这里的自动备份针对旧 v1 文件，不能理解为已经提供 v2 定时备份。v2 数据应在服务完全停止后备份整个目录，或通过 SQLite backup API 获取数据库快照；不要直接复制正在打开的 `studio.db` 并漏掉日志文件。

**回滚存在功能和可见性损失：**

- v1.2.x 仍能看到旧三引擎的 v1 项目、声音及可表示的兼容任务。
- Breeze 对象、v2 暂停/中断任务和新扩展状态只留在 v2，旧版不能显示或继续它们。
- 只有旧三引擎、终止状态、WAV 及能够诚实表示采样率等字段的任务才导出 v1 兼容清单。兼容导出失败不把 v2 成品改成失败。
- 旧版对兼容任务的“重试”仍执行旧校验逻辑，不具备 v2 的完整指纹保护。
- 不允许两个版本同时使用同一数据目录，也不提供双向同步。回滚前先停止任务服务并保存完整备份；不要直接删除 `data/v2/`。

当前开发环境的 SQLite 是 **3.50.4**。由于它不包含官方已公布的 WAL-reset 修复，当前数据库实际采用 **DELETE journal**、短事务和有界锁重试。只有运行时包含修复（3.51.3 及之后，或受支持的 3.50.7/3.44.6 回补分支）时才启用 WAL。WSL worker 不打开数据库。最终打包后端已再次实查，同为 SQLite 3.50.4 / DELETE。[SQLite WAL 文档](https://sqlite.org/wal.html)

## 桌面打包的干净输入

`npm run build:stage` 将桌面入口、构建后的前端、许可证和已经安装的生产依赖闭包复制到 `build/desktop-app/`；六个独立 Python worker 复制到 `build/desktop-resources/backend/`。随后 electron-builder 只扫描这些干净目录，以及明确指定的后端 EXE 和图标单文件，不把整个开发 `backend/` 当成资源源目录。

原因是当前 electron-builder 的 ASAR integrity 计算会递归进入资源源目录中的子目录，即使文件 filter 只列了几个 worker；直接指向开发后端会碰到 `.venv`、旧缓存 ACL 或不应打包的用户内容。阶段目录不包含模型权重、参考音频、用户 data 或开发缓存，不修改其 ACL，不关闭 ASAR integrity。

完成前端和后端构建后，可只生成本地未打包目录进行检查：

```powershell
npm run build:stage
.\node_modules\.bin\electron-builder.cmd --win --dir --publish never --config.directories.output=dist-longform-v2
```

修改源码后需要重新构建对应前端或后端，再重新 stage；不能用旧 EXE 或旧 stage 作为新源码的打包验收。`build/desktop-stage-report.json` 保存阶段文件 hash 与实际生产依赖列表。普通 `npm run build` 已串联 stage 步骤，不会自动发布。
